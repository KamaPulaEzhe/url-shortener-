# urlshortener

Небольшой сократитель ссылок на Go — учебный проект: настоящее HTTP API поверх Postgres, с контекстами и таймаутами в хранилище, graceful shutdown и приличным набором тестов под капотом.

Отправляешь длинную ссылку — получаешь короткий код. Переходишь по короткому коду — тебя редиректит на оригинал.

## Эндпоинты

| Метод | Путь | Описание |
|---|---|---|
| `POST` | `/shorten/` | Создать короткий код для URL. Тело: `{"url": "https://example.com"}`. В ответ — короткий код текстом. Повторный запрос с тем же URL вернёт тот же код — создание ссылки идемпотентно. |
| `GET` | `/{code}` | Редирект (`308`) на оригинальный URL. `404`, если код не найден. |
| `DELETE` | `/{code}` | Удалить короткий код. `204` при успехе, `404`, если такого кода не было. |

```bash
curl -X POST localhost:8080/shorten/ -d '{"url":"https://example.com/some/long/path"}'
# -> a1B2c3

curl -v localhost:8080/a1B2c3
# -> 308, Location: https://example.com/some/long/path

curl -X DELETE localhost:8080/a1B2c3
# -> 204
```

Все три эндпоинта защищены rate limiting'ом — свой лимит на каждый IP (token bucket). При превышении — `429 Too Many Requests`.

## Запуск локально

Понадобится Docker (для Postgres) и [golang-migrate](https://github.com/golang-migrate/migrate).

**1. Поднять Postgres:**
```bash
docker run --name urlshortener-pg \
  -e POSTGRES_PASSWORD=devpass \
  -e POSTGRES_DB=urlshortener \
  -p 5433:5432 \
  -d postgres:16
```
(Порт `5433`, а не стандартный `5432` — на случай, если на машине уже есть нативный Postgres на `5432`.)

**2. Настроить окружение:**
```bash
cp .env.example .env
```
Значения по умолчанию в `.env.example` уже соответствуют команде `docker run` выше.

**3. Прогнать миграцию:**
```bash
migrate -path migrations -database "postgres://postgres:devpass@localhost:5433/urlshortener?sslmode=disable" up
```

**4. Запустить сервер:**
```bash
go run main.go
```
Слушает `localhost:8080`, `DATABASE_URL` подхватывает из `.env` автоматически (через [godotenv](https://github.com/joho/godotenv)).

## Запуск тестов

```bash
go test ./... -race
```

Хранилище реализовано за одним интерфейсом `storage.Storage` в трёх вариантах — in-memory мапа (`MemStorage`), Postgres (`PgStorage`) и обёртка с кэшем поверх любого из них (`CachedStorage`) — и все покрыты тестами:

- `storage/storage_test.go` — юнит-тесты на `MemStorage`, без внешних зависимостей.
- `storage/cache_test.go` — юнит-тесты на `CachedStorage` (поверх `MemStorage`, БД не нужна), включая проверку, что попадание в кэш реально не идёт в обёрнутое хранилище.
- `main_test.go` — тесты HTTP-хендлеров через `httptest`, тоже поверх `MemStorage`, БД не нужна.
- `storage/postgres_test.go` — интеграционные тесты на реальном Postgres. Читают `DATABASE_URL` и сами себя пропускают (`t.Skip`), если переменная не задана — поэтому `go test ./...` спокойно отрабатывает и без поднятой БД, контейнер нужен только чтобы именно эти тесты реально выполнились.

## Пара решений, которые стоит объяснить

**Одна таблица, а не две.** Поиск в обе стороны (short→long и long→short) живёт в одной таблице `links` (`short_code` — primary key, `long_url` — колонка с `UNIQUE`), а не в двух отдельных мапах/таблицах. Postgres умеет строить индекс в любую сторону сам — вручную поддерживать синхронность двух структур это именно то, что расходится при параллельной записи.

**Идемпотентный `SetUrl`.** Повторная отправка того же URL возвращает тот же короткий код, а не создаёт новый каждый раз. В Postgres это обеспечивается `UNIQUE`-constraint'ом на `long_url` и обработкой конфликта при вставке, а не связкой "сначала `SELECT`, потом `INSERT`" — между этими двумя запросами есть гонка при параллельных запросах.

**`context.Context` везде.** Каждый метод `Storage` принимает `ctx` первым параметром, каждый хендлер оборачивает вызов в таймаут. Для in-memory хранилища это почти ничего не даёт (доступ к мапе и так мгновенный), но становится важным в момент, когда `PgStorage` реально ходит в сеть.

**Graceful shutdown.** `main` слушает `SIGINT`/`SIGTERM` и вызывает `http.Server.Shutdown` вместо того, чтобы просто умереть — активные запросы успевают доработать (до 10 секунд на это), вместо того чтобы оборваться на полпути.

**Rate limiting — по IP, не глобальный.** Лимит хранится отдельно на каждый клиентский IP (`map[string]*rate.Limiter` с мьютексом), а не один общий на всё приложение — иначе один агрессивный клиент выжигает бюджет и для всех остальных тоже. Устаревшие записи (клиенты, не появлявшиеся несколько минут) периодически подчищаются фоновой горутиной, чтобы мапа не росла бесконечно.

**Кэш — cache-aside, поверх интерфейса, а не поверх конкретного хранилища.** `CachedStorage` оборачивает любой `Storage` (сейчас — `PgStorage`) и реализует тот же интерфейс сам, так что для остального кода подмена прозрачна. `GetUrl` сначала смотрит в свою `sync.Map`, и только на промахе идёт в обёрнутое хранилище; `DeleteUrl` всегда сначала бьёт по реальному хранилищу (источник истины) и только потом безусловно чистит кэш — если сделать наоборот (полагаться на то, есть ли запись в кэше прямо сейчас), можно ошибочно решить, что валидная запись "не найдена" только потому что не была недавно прочитана. TTL — sliding: время жизни записи обновляется на каждое обращение, а не считается только от момента создания.

## Структура проекта

```
main.go                  HTTP-хендлеры, роутинг, запуск/остановка сервера
errs/                    sentinel-ошибки + маппинг в HTTP-статусы
middleware/              логирование запросов, recovery от паник, rate limiting
storage/                 интерфейс Storage и три его реализации (память, Postgres, кэш)
migrations/              SQL-файлы для golang-migrate
```
